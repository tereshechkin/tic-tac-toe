# Разработка веб-сайта для игры в крестики-нолики против LLM-моделей

## О проекте

Данный проект предназначен для демонстрации возможностей различных LLM (Large Language Models) в контексте классической игры "крестики-нолики". Пользователи могут играть против моделей разного уровня сложности, сравнивать их поведение и стратегии.

**Дополнительные цели проекта:**
- Отработка подходов и шаблонов реализации ИТ-проекта полного цикла;
- Практика создания страницы-лендинга с высокой конверсией;
- Реализация системы регистрации и аутентификации пользователей;
- Интеграция с внешними LLM-сервисами через API;
- Разработка личного кабинета с историей игр и статистикой;
- Внедрение системы мониторинга и сбора метрик;
- Оптимизация страниц для поисковых систем (SEO).

## Назначение и цель проекта

**Основная цель** — разработка онлайн-сервиса для игры в "крестики-нолики" с использованием LLM-моделей в качестве противника.

**Ключевые задачи:**
- Предоставить пользователям возможность играть против LLM-моделей с высоким уровнем сложности;
- Познакомить пользователей с актуальными LLM-моделями, предоставив краткое описание каждой;
- Наглядно продемонстрировать возможности современных языковых моделей в решении игровых задач;
- Собрать статистику о эффективности различных моделей для дальнейшего анализа.

## Актуальность работы

На текущий момент в интернете представлены различные сервисы для игры в крестики-нолики. Однако они имеют ряд существенных недостатков:

- Реализация на примитивных алгоритмах — выиграть против компьютера слишком просто;
- Отсутствует возможность игры по сети с другим реальным игроком;
- Ограниченный размер поля — максимальный размер у текущих аналогов 5×5;
- Отсутствие регистрации и учета истории игр;
- Нет возможности сравнения стратегий разных алгоритмов/моделей.

**Примеры аналогичных сервисов:**
- https://tictactoefree.com/ru/
- https://krestiki-noliki.ru/

## Требования

### Введение

Настоящий раздел фиксирует функциональные и нефункциональные требования к веб-сайту, необходимые для достижения бизнес-целей и удовлетворения потребностей стейкхолдеров.

Для валидации нефункциональных требований и последующего проектирования Sequence/QAS выделяются критические сценарии, подлежащие первоочередной проработке:

1. Аутентификация и получение токена (первичный вход, продление сессии, выход);
2. Запуск новой игровой сессии;
3. Вход в существующую игровую сессию;
4. Выполнение хода игроком;
5. Выполнение хода компьютером (LLM).

### Функциональные требования

Функциональные требования определяют поведение системы и её возможности с точки зрения пользователей и внешних систем.

Система должна выполнять следующие функции, разделенные на модули:

#### 1. Лендинговая страница
- Отображение общей информации об игре, правил и преимуществ;
- Отображение краткого описания доступных LLM-моделей с их характеристиками;
- Обеспечение удобной возможности перехода к странице регистрации и входа в личный кабинет;
- Обеспечение удобной возможности перехода к новой игровой сессии;
- Обеспечение удобной возможности перехода к запущенной ранее игровой сессии (для авторизованных пользователей);
- Отображение предупреждения об использовании Cookie и сбор согласий на их хранение в соответствии с GDPR/152-ФЗ;
- Обеспечение структуры и содержимого для SEO (meta-теги, заголовки, микроразметка).

#### 2. Страница регистрации и аутентификации
- Регистрация по имени, email и паролю с подтверждением через отправку кода на email;
- Вход в систему по email и коду из почты;
- Регистрация и вход через внешние сервисы через OAuth 2.0: VK ID, Google;
- Защита от автоматических регистраций (CAPTCHA или rate limiting).

#### 3. Игровая сессия
- Поддержка игры с компьютером (LLM) и с другим сетевым игроком по коду сессии;
- Возможность вернуться в начатую игру: в течение 24 часов для незарегистрированных пользователей (через Cookie), в любое время для зарегистрированных пользователей;
- Поддержка игры против следующих LLM-моделей:
  - **Рассуждающие модели:** o4-mini, o3-pro, gpt-4o;
  - **Модели без рассуждения:** gpt-5.4, gpt-5.4-mini, gpt-5.4-nano, gpt-4.1, gpt-4.1-mini, gpt-4.1-nano;
- Отображение информации о текущем ходе (чей ход, время хода);
- Поддержка следующих размерностей игрового поля: 3×3, 5×5, 10×10, 30×30;
- Поддержка следующих длин победных последовательностей: 3, 4, 5;
- Поддержка двух тем интерфейса: светлая / темная (переключение сохраняется в профиле);
- Отображение истории ходов в текущей сессии;
- Возможность сдаться и завершить игру досрочно;
- Отображение статуса игры (в процессе, победа X, победа O, ничья).

#### 4. Личный кабинет
- Отображение профиля пользователя (имя, email, дата регистрации);
- Отображение списка предыдущих игр (завершенных и прерванных) с возможностью фильтрации по дате, модели, результату;
- Обеспечение возможности возврата в незавершенную игру;
- Отображение статистики:
  - Общее количество игр;
  - Победы / поражения / ничьи;
  - Процент побед;
  - Рейтинг LLM-моделей на основе статистики побед/поражений;
  - Распределение игр по размеру поля и длине победной последовательности;
- Возможность смены пароля;
- Возможность настройки темы оформления (светлая/темная);
- Экспорт истории игр в формате CSV или JSON.

#### 5. Административная панель (для управления системой)
- Просмотр списка всех пользователей;
- Просмотр всех игровых сессий;
- Мониторинг статуса подключения к LLM-сервисам;
- Базовое управление моделями (включение/отключение);
- Просмотр общих метрик использования.

### Нефункциональные требования

Нефункциональные требования определяют качественные характеристики системы: масштабируемость, доступность, производительность, безопасность, наблюдаемость, отказоустойчивость и управляемость.

#### Масштабируемость
Система должна быть спроектирована с учетом горизонтального масштабирования:
 - Веб-сервер должен поддерживать балансировку нагрузки между несколькими экземплярами;
 - Сессии пользователей должны храниться в централизованном хранилище (Redis) для обеспечения отказоустойчивости;
 - База данных должна поддерживать репликацию и шардирование при необходимости;
 - Очереди запросов к LLM должны обрабатываться асинхронно через брокеры сообщений (RabbitMQ/Kafka).

#### Доступность
- Доступность системы должна составлять не менее 99.5% в месяц (простой не более 3.5 часов);
- Плановые обслуживания должны проводиться в периоды наименьшей нагрузки (с 03:00 до 05:00 по МСК);
- Время восстановления после сбоя (RTO) — не более 1 часа;
- Максимально допустимая потеря данных (RPO) — не более 5 минут;
- Наличие резервных каналов связи с LLM-провайдерами.

#### Производительность
- Время отклика веб-страниц (TTFB) должно составлять не более 300 мс для 95% запросов;
- Время выполнения хода игроком (от клика до отображения результата) — не более 500 мс;
- Время выполнения хода LLM-моделью:
  - Для легких моделей (nano/mini) — не более 3 секунд;
  - Для полных моделей — не более 10 секунд;
- Поддержка не менее 100 одновременных активных игровых сессий на один экземпляр сервера;
- Время загрузки лендинга при первом посещении — не более 1.5 секунды (с учетом кэширования статики);
- Оптимизация запросов к БД (индексы, кэширование часто запрашиваемых данных).

#### Безопасность
- Все соединения должны выполняться по протоколу HTTPS с использованием актуальных сертификатов;
- Хранение паролей в базе данных отсутствует;
- Реализация JWT-токенов с ограниченным сроком действия (access — 15 минут, refresh — 30 дней);
- Защита от CSRF-атак с использованием токенов;
- Защита от XSS-атак (экранирование пользовательского ввода);
- Защита от SQL-инъекций через использование ORM/параметризованных запросов;
- Rate limiting для API-эндпоинтов:
  - Регистрация: не более 5 запросов с одного IP в час;
  - Вход: не более 10 запросов с одного IP в минуту;
  - Выполнение хода: не более 1 запроса в 500 мс с одной сессии;
- Все API-ключи к LLM-сервисам хранятся в защищенном хранилище (Vault / зашифрованные переменные окружения);
- Логирование всех действий с конфиденциальными данными с последующим аудитом;
- Реализация механизма блокировки аккаунта после 5 неудачных попыток входа.

#### Наблюдаемость
- Централизованный сбор логов всех компонентов системы (ELK Stack);
- Сбор метрик производительности (Prometheus + Grafana):
  - Количество активных сессий;
  - Время отклика LLM-моделей;
  - Частота ошибок по эндпоинтам;
  - Использование CPU/RAM/Network;
  - Количество выполненных ходов в секунду;
- Сбор бизнес-метрик:
  - Количество завершенных игр по типам (победа/поражение/ничья);
  - Популярность LLM-моделей;
  - Активность пользователей (DAU, MAU);
  - Средняя продолжительность игры;
- Настройка алертов для критических событий (падение сервиса, задержки > пороговых значений);
- Структурированное логирование в формате JSON для удобства парсинга;
- Обязательное логирование Request-ID для трассировки запросов между сервисами.

#### Отказоустойчивость и управляемость
- Резервирование критических компонентов:
  - Минимум 2 экземпляра веб-сервера;
  - Репликация базы данных (Master-Slave);
  - Резервный канал к LLM-провайдерам;
- Автоматический перезапуск упавших сервисов (health checks, restart policies);
- Graceful shutdown процессов при обновлении кода (без потери текущих игр);
- Автоматическое восстановление игровых сессий при перезапуске сервера;
- Возможность горячего обновления конфигурации без перезапуска сервисов;
- Использование механизма Circuit Breaker для запросов к LLM (при ошибках — быстрый возврат fallback-ответа);
- Регулярное резервное копирование данных:
  - Базы данных — ежедневно;
  - Логов — еженедельно;
- Автоматическая ротация логов с архивацией.

### Ограничения и допущения

- Система разрабатывается для веб-браузеров последних версий (Chrome 90+, Firefox 88+, Safari 14+, Edge 90+);
- Для работы необходим доступ к интернету (все LLM-модели работают через внешние API);
- История игр для незарегистрированных пользователей хранится локально (Cookie) не более 24 часов;
- Ответственность за корректность работы внешних LLM-сервисов не несет разработчик данного сайта.

### Технологический стек

- **Фронтенд:** React + TypeScript, TailwindCSS;
- **Бэкенд:** Python (FastAPI);
- **База данных:** PostgreSQL (основная) + Redis (кэш/сессии);
- **Очереди:** RabbitMQ (для асинхронных задач);
- **Мониторинг:** Prometheus + Grafana;
- **Логирование:** ELK Stack (Elasticsearch, Logstash, Kibana);
- **Контейнеризация:** Docker + Docker compose;
- **CI/CD:** GitHub Actions.

### Критерии приемки

1. Все функциональные требования реализованы и протестированы;
2. Время отклика системы соответствует нефункциональным требованиям;
3. Проведено нагрузочное тестирование (1000 одновременных сессий);
4. Проверена безопасность (отсутствие критических уязвимостей);
5. Настроен мониторинг и алерты;
6. Проведено UI/UX тестирование с реальными пользователями;
7. Написана документация (API, архитектура, инструкция по развертыванию).
