# Требования к реализации REST API для Backend части системы

## Общее описание

Backend-часть системы представляет собой REST API сервис, реализованный на Python с использованием FastAPI. Сервис обеспечивает аутентификацию пользователей, управление игровыми сессиями, взаимодействие с LLM-моделями, хранение данных и отправку уведомлений по электронной почте.

## Модули

Модули приложения разделены по функциональному признаку для обеспечения слабой связанности и упрощения тестирования и поддержки:

### 1. IDM (Identity Management) - модуль управления идентификацией
- **Создание пользователей**: регистрация новых пользователей с валидацией email и username;
- **Блокировка пользователей**: возможность административной блокировки и автоматическая блокировка при превышении лимита неудачных попыток входа;
- **Управление верификационными кодами**: генерация, отправка и хранение кодов в Redis с TTL;
- **Управление сессиями**: учет активных сессий пользователей с привязкой к IP-адресу;
- **Управление токенами**: генерация и валидация JWT-токенов (Access и Refresh токены);
- **OAuth 2.0 интеграция**: поддержка входа через VK ID и Google;
- **Rate limiting**: защита от автоматических регистраций;
- **Полный аудит**: логирование всех действий пользователя.

Следующие данные должен храниться только в Redis, эти данные не должны сохраняться в БД:
- Активные верификационные коды;
- Токены обновления;
- Данные о временных блокировках пользователей: если код был введен не правильно более 10 раз, то пользователь (email) должен блокироваться на 5 минут.

Данные о сессиях пользователя должны сохраняться в БД в таблицу "idm_session", дополнительно данные о сессиях должны кэшироваться в Radis для более быстрого поиска.

Действия пользователя, связанные с безопасностью должны логироваться в БД в таблицу "idm_event". Типы действий, которые подлежат логированию в данную таблицу:
- LOGIN;
- LOGIN_ERROR;
- LOGOUT.

Ключи Redis:
- verification:code:{email} -> 6-значный код, TTL 5 минут
- verification:attempts:{email} -> счетчик попыток, TTL 5 минут
- verification:blocked:{email} -> флаг блокировки, TTL 5 минут
- session:{session_id} -> данные сессии, TTL 24 часа

Перед сохранением в БД и для для использования в качестве ключа Email должен быть обработан:
- Убраны все сиволы пропуска;
- Приведение к нижнему регистру всех символов.

#### Работа с JWT-токенами
Система использует двухуровневую JWT-аутентификацию:
- Access Token (краткосрочный) — для доступа к API;
- Refresh Token (долгосрочный) — для обновления Access Token.

Access Token валидируется без обращения к Redis — только проверка подписи и срока действия. Срок действия  Access Token должен быть установлен в 60 минут.
Refresh Token валидируется с обязательной проверкой в Redis. Срок действия Refresh Token должен быть установлен 30 дней.

Ключи Redis для токенов:
1. Refresh Token (активный)
   Ключ: refresh_token:{jti}
   Значение: { "user_id": "uuid", "session_id": "uuid" }
   TTL: 30 дней
2. Черный список (Blacklist)
   Ключ: blacklist:{jti}
   Значение: "revoked"
   TTL: 7 дней (до истечения срока действия токена)

Обработка ошибок:
Ошибка |	Статус |	Действие клиента
Token expired |	401 |	Использовать Refresh Token
Invalid token |	401 |	Перенаправить на логин
Token blacklisted |	401 |	Перенаправить на логин
Refresh token expired |	401 |	Перенаправить на логин
Session not found |	401 |	Перенаправить на логин

Сценарии добавления токена в Blacklist:
| Сценарий | Access Token | Refresh Token | Действие |
|----------|--------------|---------------|----------|
| **Выход из системы** (logout) | ✅ Добавляется | ✅ Добавляется | Удаление Refresh из Redis + добавление в Blacklist |
| **Блокировка пользователя** | ✅ Добавляется | ✅ Добавляется | Принудительный выход из всех сессий |
| **Обнаружение компрометации** | ✅ Добавляется | ✅ Добавляется | Немедленный отзыв всех токенов |
| **Автоматическая ротация** | ✅ (старый) | ❌ | При обновлении токена старый Access добавляется в Blacklist |
| **Истечение срока** |	❌ |	❌ |	Не нуждается в Blacklist (просто истек) |

### 2. Game Engine - модуль игровой логики
- **Реализация игровой логики**: полная реализация правил игры "Крестики-нолики" для размеров 3×3, 5×5, 10×10, 30×30 и победных последовательностей 3, 4, 5;
- **Валидация ходов**: проверка корректности ходов игроков (пользователей и компьютера);
- **Определение победителя**: автоматическое определение победителя, ничьей, подсветка победных клеток;
- **Управление состоянием игровой сессии в кэше**: хранение активных игр в Redis для быстрого доступа;
- **Управление состоянием игры**: сохранение, восстановление и завершение игровых сессий;
- **Отправка событий клиентам**: уведомление клиентов об изменениях через WebSocket (события: game_state, move_made, game_over, computer_thinking);
- **Асинхронная обработка**: использование RabbitMQ для фоновых задач (долгие ходы LLM);
- **Circuit Breaker**: защита от каскадных ошибок при взаимодействии с LLM.

Для хранения данных игровой сессии должна использоваться стратегия "Write-Behind Caching". Основная цель: не ждать записи в БД для ответа клиенту.

Основная концепция:
- Redis - источник истины для активных игр, используется для скорости;
- PostgreSQL - асинхронное хранилище для постоянного надежного хранения и резервирования;
- Запись в БД происходит отложенно и пакетно.

Ключи Redis:
- game:{game_id} -> состояние игры, TTL 24 часа.

### 3. Game Repository - модуль хранения данных игр в БД
- **Сохранение игр в БД**: сохранение завершенных и активных игр в PostgreSQL;
- **Управление игроками**: сохранение информации об игроках в игре;
- **История ходов**: сохранение всей истории ходов для последующего анализа;
- **Поиск и фильтрация**: реализация поиска и фильтрации игр по различным параметрам;
- **Статистика**: агрегация статистических данных по играм;
- **Архивация**: механизм архивации старых игр для оптимизации производительности.

### 4. Email Manager - модуль управления email-уведомлениями
- **Отправка верификационных кодов**: отправка кодов для регистрации и входа;
- **Уведомления о событиях**: отправка уведомлений о важных событиях (например, завершение игры);
- **Шаблонизация писем**: использование HTML-шаблонов для писем;
- **Очередь отправки**: асинхронная отправка через очередь;
- **Логирование**: логирование всех отправленных писем;
- **Обработка ошибок**: повторная отправка при неудаче;
- **Настройка SMTP**: поддержка различных SMTP-серверов через конфигурацию.

### 5. LLM Manager - модуль управления LLM-моделями
- **Взаимодействие с LLM через API**: унифицированный интерфейс для работы с различными LLM-провайдерами (OpenAI, Anthropic, Google, и др.);
- **Формирование промпта по шаблону**: генерация промптов с учетом контекста игры и уровня сложности;
- **Верификация ответа от LLM**: проверка корректности ответа (ход должен быть валидным);
- **Управление моделями**: включение/отключение моделей, получение списка доступных моделей;
- **Мониторинг производительности**: отслеживание времени ответа и частоты ошибок для каждой модели;
- **Кэширование ответов**: кэширование ответов для часто встречающихся позиций в Redis;
- **Управление API ключами**: безопасное хранение и ротация API ключей.

На первом этапе планируется подключить следующие модели LLM:
- OpenAI:
 - gpt-4-turbo;
 - gpt-4o-mini;
 - o4-mini;
 - gpt-4.1-mini;
 - gpt-4.1;
- Anthropic:
 - claude-opus-4-6;
 - claude-sonnet-4-6;
 - claude-haiku-4-5;
- Google:
 - gemini-2.5-flash;
 - gemini-2.5-pro.

### 6. Admin Module - модуль администрирования
- **Управление пользователями**: просмотр, блокировка, редактирование пользователей;
- **Управление игровыми сессиями**: просмотр всех игр, принудительное завершение;
- **Мониторинг LLM-сервисов**: просмотр статуса подключения к LLM-провайдерам;
- **Управление моделями**: включение/отключение моделей, добавление новых моделей;
- **Просмотр метрик**: доступ к общим метрикам использования системы;
- **Аудит**: просмотр логов действий пользователей и системных событий.

### 7. WebSocket Module - модуль WebSocket-соединений
- **Управление подключениями**: установка и управление WebSocket-соединениями для активных игр;
- **Broadcast событий**: отправка событий всем подключенным клиентам в игровой сессии;
- **Обработка сообщений**: обработка сообщений от клиентов (ходы, запросы хода компьютера);
- **Восстановление соединения**: поддержка восстановления соединения при разрывах;
- **Проверка прав**: валидация прав доступа к игровой сессии;
- **Мониторинг соединений**: отслеживание активных соединений для статистики.

## Swagger

К REST API должен быть подключен Swagger (FastAPI автоматически генерирует документацию):
- Документация доступна по адресу: `/docs` (Swagger UI);
- Альтернативная документация: `/redoc` (ReDoc).

Все эндпоинты должны быть аннотированы с использованием Pydantic схем для автоматической генерации документации и валидации.

## Логирование

- Использовать структурированное логирование в формате JSON с использованием библиотеки `structlog`;
- Уровни логирования: DEBUG, INFO, WARNING, ERROR, CRITICAL;
- Обязательное логирование Request-ID для трассировки запросов;
- Логирование всех запросов к API (метод, путь, статус, время выполнения);
- Логирование ошибок с полным стектрейсом;
- Отдельное логирование действий с конфиденциальными данными;
- Ротация логов с архивацией;
- Интеграция с ELK Stack для централизованного сбора логов.

На первом этапе логирование должно выполняться в файлы, подключение ELK будет выполнено позже.

## Чистота кода

- Использование типов (type hints) для всех функций и методов;
- Соблюдение PEP 8 (использовать линтеры: flake8, black, isort);
- Документирование всех публичных функций и классов (docstrings);
- Разделение ответственности: каждый класс/функция должны иметь одну ответственность;
- Использование Dependency Injection для слабой связанности;
- Покрытие кода тестами (минимальный порог: 80%);
- Использование паттернов проектирования (Repository, Service, Factory, Singleton);
- Обработка всех исключений с понятными сообщениями для пользователя.

## Дополнительные требования

1. **Файл README.md** в корне `restapi/` должен содержать:
   - Общее описание проекта;
   - Инструкцию по созданию виртуального окружения;
   - Инструкцию по установке зависимостей;
   - Инструкцию по настройке переменных окружения;
   - Инструкцию по запуску приложения (включая режим отладки);
   - Инструкцию по запуску тестов;
   - Инструкцию по работе с миграциями;
   - Описание структуры проекта.

2. **Файл requirements.txt** должен содержать все зависимости проекта без указания версий (будут использоваться последние версии библиотек).

3. **Переменные окружения** должны быть описаны в `.env.example` с комментариями для каждой переменной.

4. **Миграции БД**: использовать Alembic для управления схемой БД.

5. **Health Check**: реализовать эндпоинт `/health` для проверки состояния сервиса.

6. **Graceful Shutdown**: корректное завершение работы с сохранением состояния активных игр.

7. **Мониторинг**: интеграция с Prometheus для сбора метрик:
   - Количество запросов по эндпоинтам;
   - Время выполнения запросов;
   - Количество ошибок;
   - Активные WebSocket соединения;
   - Состояние подключения к LLM.

8. **Документация API**: все эндпоинты должны быть детально документированы в Swagger с примерами запросов и ответов.

На первом этапе ключи должны храниться в файле .env.

Перечень параметров, которые должны быть вынесены в .env:
- Данные для подключения к БД Postgres;
- Данные для подключения к SMTP-серверу;
- Данные для подключения к Redis;
- Данные для подключения к RabbitMQ;
- Ключ для подключения к API для OpenAI;
- Базовый URL для подключения к API для OpenAI (планируется подключаться через Proxy API);
- Ключ для подключения к API для Anthropic;
- Базовый URL для подключения к API для Anthropic (планируется подключаться через Proxy API);
- Ключ для подключения к API для Google;
- Базовый URL для подключения к API для Google (планируется подключаться через Proxy API);
